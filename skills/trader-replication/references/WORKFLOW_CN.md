# 复刻动态流程（trader-replication-loop）

本文件是 `.claude/workflows/trader-replication-loop.js` 的规则来源。脚本只管编排，判断标准都写在这里；两边冲突时以本文件为准。

## 一、防漂移

迭代中最容易漂移的是：尺子被换、目标被放宽、底座悄悄回到参照系统、同一机制反复试、选股和交易混在一起评。所以以下由用户掌握，任何 agent 和 Codex 都不能改：

- **本文件**、各交易员的**档案**（`config.json` 的用户节，清单见第九节），以及尺子和判定代码（`studies/trader_replication/pipeline.py`、`funnel.py`、`mainleg.py`）。每次运行开始时记下它们的指纹，每轮开头重新核对；变了就立刻停下，报告“规则漂移”。改这些就是改规则，须用户同意，旧轮次判定不回改。
- **数据集白名单**：`datasets` 节逐个登记可用数据集，包括名称、Release tag、本地路径、`CHECKSUMS.sha256` 的 SHA，以及 schema（文件、列名与类型、市场、日期范围、标的数）。要求如下：
  - 流程里只能读登记过的数据集，以及经 `studies.trader_data` 由它们派生的缓存；
  - 不新增、不修改、不替换数据集，不改 schema，也不在代码里引用未登记的数据路径；
  - 每轮“量”都核对文件与 CHECKSUMS、schema 是否一致，不一致按固定卡失败停下；
  - 方案需要新数据或改数据时，直接进检查点，写明需要什么数据、为什么，等用户同意后由用户改 `datasets` 节；
  - 新登记的 `datasets` 节要用户确认后，把 `approved_by_user` 填上日期才生效，没填就不开轮。
  - 白名单约束的是轮次里的策略与评测代码（候选、尺子、账户回放）。仓库里既有的回归测试会读它们自己的历史缓存，这不算轮次用数据，但测试的临时文件要写到本轮 `work/tmp`（第七节）。（WF-042/043/054，2026-11-09 检查点裁定）
- **阈值只写在 config**，代码从 config 读，不写死数字；本文件只讲含义。
- **判定由 Codex 在轮末调用 `pipeline.accept` 算出**，写进 completion.json，核对步骤重算一次，记账只照抄。
- **留出年结果不进入下一轮设计的输入**：历史记录只带选择年，留出年只决定是否进检查点。
- **`goal` 写用户原话**。每轮写任务书和判定时逐条对照，说明本轮怎样更接近目标。“收益更好但更不像他”只能记作探索分支。
- **总账只追加，不改写。**设计前必须查；与失败轮次实质重复，审查时判为致命问题。
- **流程自身的改进只走提案**：轮次里发现规则不清、尺子缺陷、工具缺失、任务书老坑，只记进流程问题账（第八节），不在轮次中改规则。用户批准的规则改动，也只在没有 Codex 单元运行时落盘（WF-010：WF00 运行中改规则触发漂移停止）。
- **新交易员起步**：先起草他的 WF00 任务书和 `config.json`，停下等用户确认 `goal` 和阈值；用户确认后在 `rounds/WF00/` 放一个 `APPROVED` 文件，没有这个文件就不启动 Codex。

## 二、架构：一个行情层，三条线，一个合并验收

```
行情层：每天给出一个状态（只读市场数据），三条线共用
  │
  ├─ 选股线：每晚点的几只里有没有他的票            不跑账户
  ├─ 交易线：拿到他的票能不能赚钱、拿到峰前          测试台直接喂他的票
  └─ 衔接线：点名之后怎么分配名额和仓位、能不能真买进   用前两条线的冻结版本
  │
合并验收：峰前持有 + 成功标准（行为、账户）
```

- **先全局，后局部**：每轮先看完整漏斗（L0–L6）、行为记分卡和分状态收益，再决定这轮改哪里。损失只落在一层时做**单线轮**（只改这一条线，另两条用冻结版本）；几层的损失互相牵连时（例如点到了却买晚、仓位小，弱势态缺空头），做**联动轮**（`line=joint`，见第四节），把相关环节一起改（用户 2026-11-09：“所有可修改的环节都可以考虑修改，而不是一次只改一个地方等着推进”）。
- **单线迭代**：运行时用参数 `line`（可加 `scope`）指定只练一条线，例如 `line=selection`。
  - 这次运行的每一轮都只在这条线上定格；
  - 被接受的版本照常写进该线的冻结版本，但合并验收推迟到运行结束；
  - 检查点报告写明“待合并”，下一次不带 `line` 的运行，第一轮必须做合并验收。
  - 不带 `line` 时照旧：有线被接受，下一轮立刻合并。
- **每条线自己的尺子、可达上限和总账标签**，见第四节。
- **合并验收没过时**，用持仓漏斗判断丢在哪条线，回那条线继续，不在合并层面调参数。
- 固定卡保留在两头：开头是 G0 资料台账、G1 数据与引擎无未来函数；结尾是成功标准（G4 行为、G5 账户）和 G6 冻结，冻结要用户同意。

## 三、分行情：共同版本 + 分状态修正

每条线的配置都分两部分：

- `common`：不分行情的共同版本；
- `by_state.<状态>`：某个行情状态下的修正。

修正内容按线划分：

| 线 | 修正什么 | 例子（Martin） |
|---|---|---|
| 选股 | 看哪类形态、哪档票（高波动小盘 / 大票）、哪些题材，每晚名额 | 进攻态点高波动题材小盘；2026 年那类状态转向大票 |
| 交易 | 做不做、做多大、做多还是做空、止损和离场松紧；同时持仓数（与衔接线共有，按 `capital.optimizable`，2026-11-09 裁定） | 进攻态早买、收盘才止损、放大仓位；防守态不开新多，只做第一次跌破 50 日线后的反抽空 |
| 衔接 | 名额和仓位分给哪档、同时持仓上限、换仓 | 进攻态名额给新起来的题材 |

规则：

1. **先共同版本，后修正。**行情层冻结之前，只能改 `common`；档案 `regime.enabled=false` 的交易员永远只有 `common`。
2. **状态数、开关数以档案 `regime` 节的上限为准**（默认状态最多 3 种、开关最多 2 个），每个开关都要逐字对应他的一句原话。先做市场级；题材级（2026 年 7 月的差异在题材层面，指数看不出来）等市场级冻结、漏斗显示仍有按题材丢的段时再开。
3. **每条线每个状态最多 2 项修正**，修正幅度要能说清理由（共同版本加收缩修正，防止小样本凑数）。
4. **有他样本的状态**：修正按行情段（episode）留一检验。**没有样本的状态**：按原话写，标“未观测”，不参与选择，冻结后由前向记录检验。
5. **分状态的目标画像来自他的台账**：先按年、按月、按状态核对他做多还是做空、做哪档票、什么形态，再对照我们系统的月度盈亏。不能直接采信统计检验的 p 值。台账逐年记录密度不同，不比笔数密度。
6. **行情状态只读市场数据和本系统已知的点名**，不读他的台账、段表和账户结果。
7. **量和用分开**：
   - **量**：冻结的状态日历由所有版本共用（包括底线 v0），只用来分状态拆账。
   - **用**：某版本在执行中按状态切换配置，这是版本组件；版本可以不用，用了就写明用哪份日历、改了哪几项。
8. **执行开关（`by_state` 修正）的接受**：和同一版本关掉这项修正相比，以下三条要同时满足：
   - 该状态下我们的行为更接近他在该状态下的行为（行为项见档案 `behaviour_card`）；
   - 该状态下他的段峰前持有不减；
   - 每年不亏。

   只让收益变好、行为没更像他的，记作探索分支。

## 四、各线的尺子与接受条件

所有线都要满足：选择年（Martin：2024、2025）只用于选择，留出年（2026，标“留出*”）只测一次；+3 段以内的差别算噪音。

### 行情层

- 定义来自他的原话和标准参数，只取常见值，不做拟合。
- 冻结条件：
  - 只用当日之前的市场数据；
  - 定义扰动后的日重合率 ≥ 90%；
  - 每个状态对得上他的一句原话（档案 `regime.words`）；
  - **主依据**：在他选择年的台账上，各状态下的做法有差别，且方向与原话一致。看多空比例、频率、买点形态、票档、仓位或持有，至少一项。台账记录太少时按原话，标“证据弱”。
- 参照账户分状态收益只报告，不作冻结依据，因为它反映的是我们系统，不是他。
- 冻结后写入 `state.json.components`，三条线引用同一份。

### 选股线

- 口径：每晚新点 K=3 只、10 晚冷却（S 口径）。
- 主尺：他的段在早期合格夜被点到的段数。
- 护栏：不限 K 时平均每晚新点名 ≤5，按方案实际输出的名单算，保留方案自带的每晚上限，只去掉外层 K=3（WF-011，用户 2026-11-09 定）；每年点过的不同票数不比比较对象多 20% 以上。
- 接受：选择年合计 +3 段，且每年都不降。
- 分状态报告：各状态下他的段被点到的比例。

### 交易线（测试台）

- 输入：他的每一段，在 [首锚点−3, 峰前1日] 内每晚都把他的票当作“已点名”，买点、止损、仓位、离场全由我们的执行决定。
- 对照：同一晚我们点名里不是他的票，用同一个执行一起跑。
- 主尺：他的段峰前一日仍持有的段数，以及在他的段上的盈亏比和平均 R。
- 护栏：对照票合计不比比较对象差；行为记分卡（胜率、盈亏比、持有天数）在 ±20% 内的项数不减。
- 接受：峰前持有 +3 段，他的段平均 R 不降，护栏都满足。
- 这个测试台只用来评执行；最终系统的策略代码仍然不许读他的台账（三层对照第二层）。
- **留出年**：测试台每晚都喂他的票，收益偏高，判不出“每年不亏”。所以交易线的留出年只报告，每年亏不亏留到合并验收用完整账户判。（WF-063，2026-11-09 检查点裁定）
- **起点和比较对象每笔风险不同时**：`pipeline.accept('trading')` 的对照护栏按绝对盈亏算，量不出差别。任务书在选择条件里补一条和仓位大小无关的护栏，用已平仓对照票的 R 之和，只许更严，不改 accept。改尺子的提案已批准，在两次运行之间实现。（WF-070、WF-067）
- **改执行引擎**：轮次里不改共享引擎（`studies/trader_replication/system.py` 等冻结缓存指纹覆盖的代码）。在交易员目录里放一份副本，先证明默认参数下和原引擎逐位一致，再加新参数。（WF-062、WF-068）
- **诊断起点**：上一次运行里离合并门槛只差一两段的探索分支（Martin：WF01 的 W1E），可以作为交易线测试台的执行起点，候选在它上面改。接受时仍和冻结版本比：测试台上和冻结执行比，合并时和当前合并主线比。分支本身不因此变成底座或新版本。

### 衔接线

- 输入：选股线和交易线的冻结版本。
- 主尺：持仓漏斗里“点到 → 早买 → 峰前持有”的转化。
- 接受：峰前持有 +3 段，选择年每年不亏。

### 联动轮（line=joint）

- 一个候选可以同时改选股、交易、衔接的 `common`，以及行情层冻结后的 `by_state` 修正；档案上限照旧（每条线每个状态最多 2 项修正、开关数和状态数不超过 `regime` 上限、资金档位不越 `capital`）。
- `scope` 写明改了哪些“线 × 状态”。
- 判定用下文合并验收（完整账户 + 持仓漏斗），比较对象是当前合并主线（没有就用 `base` 组成的 v1）。
- **必须做消融**：被选中的候选，逐个去掉其中一个改动各跑一次，报告每个组件对峰前持有、行为记分卡和每年收益的贡献；去掉后不变差的组件不进入新版本。
- 被接受时，各改动线的冻结版本和合并主线一起更新，版本号加 1；不另走 pending_merge。
- 各线自身的主尺和护栏照常报告，只作参考，不作否决。

### 合并验收

- 持仓漏斗（以冻结段表为分母，每段按最早丢失的层只计一次）：

  | 层 | 含义 |
  |---|---|
  | L0 | 不在池 |
  | L1 | 未点名 |
  | L2 | 未触发 |
  | L3 | 未成交 |
  | L4 | 买晚 |
  | L5 | 早买后被洗 |
  | L6 | 峰前持有 |

  其中 L0–L1 归选股线，L2–L3 归衔接线，L4–L5 归交易线。
- 接受新的合并主线需同时满足：
  - 选择年每年不亏；
  - 峰前持有合计比当前合并主线多 3 段以上，且每年都不少；
  - 峰前持有段的仓位占比不降；
  - 行为记分卡在 ±20% 内的项数不减。
- **保真接受**（第二种接受方式，2026-11-09 WF06 检查点裁定，对应 `goal`“框架内最像他、每年不亏、收益不能差太多（尤其 2025）”）：段数不增、但收益和风险更像他的改动，同时满足以下各条即可接受：
  - 选择年每年不亏；
  - 峰前持有每年都不少于当前合并主线；
  - 峰前持有段的仓位占比不降；
  - 行为记分卡在 ±20% 内的项数不减；
  - 与他的对数收益差 |log((1+版本)/(1+他))|：每个选择年扩大不超过 `accept.merge.fidelity_max_year_gap_loss`，两年合计至少缩小 `accept.merge.fidelity_min_log_gap_gain`（Martin 两项都取常见值 0.1，约等于收益相对差 10%；定这两个数时已看过 WF06 的粗估，按粗估 E1 不一定能过，没有为了让它过而调）。

  判定由 `pipeline.accept('merge')` 一并给出，结果里写明按哪种方式接受。两种方式都只看选择年；接受后版本号照样加 1。保真接受后，下一轮不得再用这种方式回退已接受的段数。
- 还没有合并主线时，比较对象用底线参照（Martin：master）。底线参照只作比较对象，不作底座：它的选股、执行、分配都不能作任何一条线的冻结起点，候选也不得沿用它的成交额排序选股。
- 各线的冻结起点（底座）写在 config 的 `base` 节，由用户定（Martin：IE47 选股 + C062 执行与分配，2026-11-09）。起步和换版本时，冻结版本只能是 `base`，或者在 `base` 之上被接受的版本。
- **资金与杠杆**：杠杆指多空持仓总市值 ÷ 权益，按交易员写在 config 的 `capital` 节，由用户定。
  - **档位**：每档有开仓上限 `initial`、维持线 `maintenance`（权益 ÷ 持仓市值的最低比例）和融资利率。Martin 有三档：L1 现金 1 倍；L2 普通融资 2 倍 / 维持 25%；L2.8 他的峰值 2.8 倍 / 维持 30%。
  - **验收档** `acceptance_profile`（Martin：L2.8）：所有方案、参照系统和版本都在同一档下比较，判定只看这一档；其他档只作对照。
  - **追保**：每天收盘检查，杠杆超过 1/维持线时，第二天开盘减仓，一直减到开仓上限以内，跳空损失照实计入。在开仓上限和维持线之间时，不开新仓、不加仓，也不强制卖。追保时点由用户定，不可优化。
  - **可优化的部分**：档位内用多少杠杆、减仓方式、单只仓位上限、同时持仓数，属于衔接线和交易线的配置，可以按状态设。减仓方式只能在 `deleverage_methods` 里三选一，即先砍最弱（按浮动 R 从低到高）、按比例、先卖最大，默认先砍最弱。

### 版本号

- **一个版本号代表一整套系统**（行情层 + 选股 + 交易 + 衔接），按顺序编号：
  - `v0` 是底线参照（`config.bar`，Martin：master），只作比较；
  - `v1` 是底座（`config.base`，Martin：上周最佳，IE47 + C062）；
  - 之后每通过一次合并验收加 1。
- 单线被接受、还没合并的改动，记作“v1 + 选股候选”这类写法，合并通过才有新版本号。
- 汇报只说版本号；组件名只写在版本明细里。
- **版本总表** `workflow/VERSIONS_CN.md`（由 `versions.json` 生成，只追加）：
  - 每个版本一行，用同一张记分卡，和他本人并排；
  - 年份含选择年和留出年，留出年标“留出*”；
  - 写明“开关”：无，或者日历名加修正项数；
  - 按共用日历分状态列出：行为离他多远、他的段峰前持有、收益与回撤；
  - 附“开关对照”：同一版本开关开、关各跑一次的差值；
  - 附“档案对齐”：档案每一项本版本是否在范围内；
  - 检查点报告的第一张表就是它。
- 各项按状态分开报告。资金纯度、毛利纯度、撒网比例只报告，不做门槛。

## 五、每轮怎么走

| 步骤 | 做什么 | 模型 |
|---|---|---|
| 量 | 核对规则指纹；读上一轮 Codex 写好的 `STATUS.json`（各线 × 各状态：当前值、目标、可达上限、冻结版本），不跑重计算 | Sonnet，低推理 |
| 定格 + 设计 | 见下文 | Opus |
| 审查 | 独立挑错，最多改两次。清单见下文 | Opus |
| 跑 | Codex 执行：预登记 → 选择 → 留出一次 → 报告 → `pipeline.accept` 判定 → 重出 `STATUS.json` | Sonnet，低推理（只负责启动和等待） |
| 核对 | 流程：时间顺序、只用选择年、登记版、看板和判定代码未改、测试全过；数据集核对与改动代码的路径扫描都通过。数字：从 json 复算关键数，漏斗分层之和等于段数，重算判定 | Sonnet |
| 记账 | 照抄已核对的判定，写总账和 state | Sonnet，低推理 |

**定格 + 设计**：

- 先看全局：完整漏斗、行为记分卡、分状态收益，判断损失落在一层还是几层连着；再挑格子：单线轮挑一个“线 × 状态（或 common）”，联动轮写明一组“线 × 状态”。
  - 规则：先看合并漏斗丢段最多的线；再看该线可补段数，即 min(离目标的差, 可达上限 − 当前值)。
  - 前一轮有线被接受时，本轮必须做合并验收。
- 查总账，写清和旧轮次差在哪。
- 从他的原话和漏斗逐段数据两个角度出方案。
- 写任务书，最多 5 个候选。
- **组件放行**：凡是从少数几段的准入或成交记录里想出来的组件，先在全账本上用同口径做单票回放检验，结果持平不算通过；放行规则在预登记前写死，不通过的组件不进候选。可达上限以当前合并主线为基准算，分支只作诊断。（WF-048/050/051）
- **腾名额类方案先量占位**：假设“名额被占”的方案，任务书要先从上一轮记录里量出占着名额的持仓是什么状态（当晚 R、入场以来最高 R、持有天数）。可达上限只算被 `max_open` 挡住的那些晚上，并扣掉当晚排在他的票前面的其他被挡候选。accept 的每一项（段数、行为项、对照）都先列出起点差距。（WF-083/084/086）
- **底线项只报告**：hard_lines 里的胜率上限、每年笔数、对数收益差（“收益不能差太多，尤其 2025”），由核对步骤逐年列出，检查点报告必须写出来。目前 v1 本身就过不了对数收益差这一条，所以暂时只报告，不作接受门槛，等用户另定。（WF-034）

**审查清单**：

- 未来函数；策略侧是否读了他的台账、票名、日期、段表；
- 是否只用 `datasets` 白名单里的数据，有没有新增或改动数据、引用未登记路径；
- 选择和留出是否分开；参照账户和比较对象是否事先写死；可达上限是否先算；
- 是否只改了声明的线和格子；
- 翻译和实现上的老坑：宽止损配固定风险导致仓位太小（H1）；小试仓占满名额（H2）；加仓后止损没跟上（H2）；过滤过严导致可达上限过低（H2）；冷却挡住再买（P5）；止损只有约半个 ADR、盘中被扫（P5）；选错参照账户（P5）；
- 是否与总账中失败的轮次实质重复；
- 执行时点单测是否先写；
- 是否超出本轮的计算范围（重算没改的线、重放已登记的旧系统、不读冻结缓存）。

每轮约 6 个 agent，其中 Opus 2 个；审查每改一次多 2 个。

**每类轮次的计算范围**：只算被改的那条线，其余读冻结缓存。

| 轮次 | 只跑 | 不跑 | 计算上限 |
|---|---|---|---|
| 选股 | 候选的每晚点名，加上选股主尺和护栏（分状态） | 账户、测试台、漏斗 | 15 分钟 |
| 交易 | 测试台：他的段和同晚对照票 | 选股、整账户 | 15 分钟 |
| 行情 | 状态序列；参照账户分状态收益（读缓存台账） | 重放账户 | 15 分钟 |
| 衔接 | 冻结点名加冻结执行下的账户与漏斗 | 重算点名、测试台 | 45 分钟 |
| 合并 | 完整账户与漏斗 | 无 | 45 分钟 |
| 联动 | 改到的线的点名或执行，加完整账户、漏斗与消融 | 没改到的线（读冻结缓存） | 60 分钟 |

- **冻结缓存**：放在 `workflow/frozen/<线>/<版本>/`，内容是冻结版本的每晚点名、测试台输入和参照账户台账，带代码与数据指纹。
  - 各轮只读，不重算。
  - 冻结版本变了才重建；缺了由该线下一轮先建一次，建缓存不算候选。
- 计算超过上限就停下，在报告里写明原因，不加跑。
- `STATUS.json` 只重算本轮那条线的格子，其余格照抄上一轮，并保留指纹。

**检查点**（满足任一就停下，交给用户）：

- 本次运行跑满预定轮数（默认 3 轮）；
- 同一格连续 2 轮没有进步；
- 审查两次都没过；
- 留出年一次检验亏钱；
- 规则漂移；
- 固定卡失败；
- 合并验收达到成功标准。

检查点报告除了策略进展，还要列出流程问题账里未处理的提案（见第八节）。

## 七、Codex 子步骤

- 不开 fast 或 priority：不加 `service_tier`。
- 模型和推理强度由 workflow 参数 `codex_model`、`codex_effort` 指定，默认 `gpt-6.1-terra` + `max`；命令里显式传，不依赖 `~/.codex/config.toml` 的默认值。
- 同一时间只跑一个重计算单元，`CPUQuota=60%`，最多两核。

```bash
cd <worktree> && n=<id>; d=studies/<trader>/workflow/rounds/$n; mkdir -p $d/logs; LOG=$PWD/$d/logs/codex.log
systemd-run --unit=codex-$n --collect -p CPUQuota=60% -p AllowedCPUs=0-1 -p Nice=10 -p IOSchedulingClass=idle \
  -p StandardOutput=file:$LOG -p StandardError=file:$LOG -E HOME=/root -E PATH="$PATH" --working-directory=$PWD \
  codex exec -m <codex_model> -c model_reasoning_effort="<codex_effort>" --dangerously-bypass-approvals-and-sandbox \
  "按 $d/PLAN_CN.md 执行。任务书就是全部要求。" </dev/null
```

等待时不用前台 `sleep`。重复执行下面这条，直到单元结束：

```bash
pid=$(systemctl show -p MainPID --value codex-$n); [ "$pid" != 0 ] && timeout 570 tail --pid=$pid -f /dev/null; systemctl is-active codex-$n
```

命令环境：本机 locale 不是 UTF-8。启动 Codex 单元时统一用 `-E PYTHONUTF8=1 -E LC_ALL=C.UTF-8` 设好，单元里的命令不必再写，漏写也不算违反约束（WF-074）。第七节所有命令（数据集与档案检查、测试）都在这个环境下运行；测试设 `TMPDIR=<轮次>/work/tmp`，日志写进文件。（WF-042/043/054）

测试范围：每轮只跑 `custody/tests`（每次必跑）和本轮改到的切片测试。Martin 的轮次是 `studies/trader_replication/tests`、`studies/martin_luk/tests`。改了看板或数据加载才加跑对应切片。

数据和磁盘：

- 只用 `datasets` 白名单（见第一节）。不新建数据集，也不另存同一份行情的面板副本，面板一律走 `studies.trader_data` 的缓存。核对命令：`.venv/bin/python -m studies.trader_replication.datasets check --config <config.json>`；扫描本轮改动代码：`... datasets scan --config <config.json> --git-diff`。
- 本轮中间文件只放 `rounds/WFnn/work/`。轮末只保留 completion.json 里 `keep` 列出、下一轮或报告复算真正要用的文件，合计不超过 100MB，其余删掉；completion.json 记下轮前、轮后的磁盘剩余。
- 磁盘剩余低于 800MB 时，先清本轮自己的中间文件；还不够就停下报告，不碰本轮以外的东西。
- completion.json 带 `workflow_issues` 数组：本轮执行中发现的流程问题（任务书写错或含糊、缺工具、规则互相冲突、尺子算不出），没有就写空数组。

## 八、流程问题账：复刻 Martin 的同时改进流程

`skills/trader-replication/references/workflow_issues.jsonl` 由所有交易员共用，只追加，不改写，不算进规则指纹。

- **谁记**：
  - 审查的致命和次要问题里，属于流程而非本轮方案的；
  - 核对发现的问题；
  - Codex 在 completion.json 里写的 `workflow_issues`。
  - 以上三类都由记账步骤追加。
- **每行字段**：`id`、`date`、`trader`、`round`、`step`（量 / 定格 / 审查 / 跑 / 核对 / 记账 / 起步）、`kind`（规则不清 / 尺子缺陷 / 工具缺失 / 任务书老坑 / 成本）、`evidence`（文件路径或数字）、`proposal`（具体改哪份文件的哪一处）、`general`（换一位交易员是否同样成立）、`status`（open / approved / rejected / applied）。
- **改状态**：另追加一行，带 `ref` 指向原 id。同一问题第二次出现时，也追加一行引用原 id，不新开问题。
- **检查点**：最多列 3 条提案，按出现次数和对结论的影响排序，通用的在前。每条写清改什么、为什么、对已有轮次判定有无影响。
- **生效**：用户同意后，在两次运行之间改本文件或判定代码，追加 `applied` 行；下次运行重新取指纹。旧轮次判定不回改。审查清单里的“老坑”只从这里批准后加入。

## 九、交易员档案：复刻必须考虑、必须被衡量的条件

档案描述的是交易员本人：他要达到什么，在什么数据、账户和行情条件下交易，行为长什么样。它不描述我们的方案。版本只能在档案范围内选择怎么做。

- **存放**：档案存在 `config.json` 的用户节，由 `workflow/PROFILE_CN.md` 生成给人看。用户节全部计入规则指纹。
- **起步时必须填完**：新交易员的 WF00 先起草档案，用户确认后才开轮。每一项要么有值，要么写明“不适用”或“证据弱，按原话”，并附理由。缺项时 `profile check` 判失败，不启动。
- **每一项都要有两样东西**：
  - 来源：原话出处、台账统计或用户决定，带日期；
  - 怎么衡量：对应版本总表或接受条件里的哪一列。

  没有衡量列的档案项，不算登记。

| 档案项 | 内容 | 约束方式 |
|---|---|---|
| `goal` | 用户原话目标 | 每轮逐条对照 |
| `hard_lines`、`accept`、`checkpoint` | 底线、各线接受条件、检查点 | 判定 |
| `datasets` | 数据白名单与 schema | 每轮核对 |
| `bar`、`base` | 底线 v0、底座 v1 | 版本起点 |
| `capital` | 杠杆档位、验收档、追保时点、可优化项的范围 | 硬上限加可优化范围 |
| `regime` | 是否随行情改变做法（`enabled`）、原话、状态与修正上限、冻结的日历 | 第三节和第四节 |
| `behaviour_card` | 他的行为画像：胜率、盈亏比、笔数、持有，以及多空、形态、票档；有出处的按年、按状态写 | 版本总表行为列，±容差 |
| 选择年、留出年、段表 | 评测口径 | 判定 |

- **每轮都要对齐档案**：
  - 定格写明候选触及哪些档案项；
  - 审查查候选是否越出档案范围；
  - 核对出“档案对齐”表；
  - 记账把对齐结果写进总账。
- **改档案**：只能由用户改，在两次运行之间，追加 `change_log`。旧轮次判定不回改；受影响的冻结项标“待重判”。
- **优化中发现档案缺项或有错**：记进流程问题账，在检查点提给用户，不在轮次里自己补。
