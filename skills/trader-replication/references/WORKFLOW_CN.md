# 复刻动态流程（trader-replication-loop）

本文件是 `.claude/workflows/trader-replication-loop.js` 的规则来源。脚本只管编排，判断标准都写在这里；两边冲突时以本文件为准。

## 一、防漂移

迭代中最容易漂移的是：尺子被换、目标被放宽、底座悄悄回到参照系统、同一机制反复试、选股和交易混在一起评。所以以下由用户掌握，任何 agent 和 Codex 都不能改：

- **本文件**、各交易员 `config.json` 的 `goal`、`hard_lines`、`accept`、`checkpoint` 四节，以及尺子和判定代码（`studies/trader_replication/pipeline.py`、`funnel.py`、`mainleg.py`）。每次运行开始时记下它们的指纹，每轮开头重新核对；变了就立刻停下，报告“规则漂移”。改这些就是改规则，须用户同意，旧轮次判定不回改。
- **阈值只写在 config**，代码从 config 读，不写死数字；本文件只讲含义。
- **判定由 Codex 在轮末调用 `pipeline.accept` 算出**，写进 completion.json，核对步骤重算一次，记账只照抄。
- **留出年结果不进入下一轮设计的输入**：历史记录只带选择年，留出年只决定是否进检查点。
- **`goal` 写用户原话**。每轮写任务书和判定时逐条对照，说明本轮怎样更接近目标。“收益更好但更不像他”只能记作探索分支。
- **总账只追加，不改写。**设计前必须查；与失败轮次实质重复，审查时判为致命问题。
- **新交易员起步**：先起草他的 WF00 任务书和 `config.json`，停下等用户确认 `goal` 和阈值；用户确认后在 `rounds/WF00/` 放一个 `APPROVED` 文件，没有这个文件就不启动 Codex。

## 二、架构：一个行情层，三条线，一个合并验收

```
行情层：每天给出一个状态（只读市场数据），三条线共用
  │
  ├─ 选股线：每晚点的几只里有没有他的票            不跑账户
  ├─ 交易线：拿到他的票能不能赚钱、拿到峰前          测试台直接喂他的票
  └─ 衔接线：点名之后怎么分配名额和仓位、能不能真买进   用前两条线的冻结版本
  │
合并验收：峰前持有 + 成功标准（行为、账户）
```

- **一次只改一条线**，另外两条用冻结版本，不动。
- **每条线自己的尺子、可达上限和总账标签**，见第四节。
- **合并验收没过时**，用持仓漏斗判断丢在哪条线，回那条线继续，不在合并层面调参数。
- 固定卡保留在两头：开头是 G0 资料台账、G1 数据与引擎无未来函数；结尾是成功标准（G4 行为、G5 账户）和 G6 冻结，冻结要用户同意。

## 三、分行情：共同版本 + 分状态修正

每条线的配置都分两部分：

- `common`：不分行情的共同版本；
- `by_state.<状态>`：某个行情状态下的修正。

修正内容按线划分：

| 线 | 修正什么 | 例子（Martin） |
|---|---|---|
| 选股 | 看哪类形态、哪档票（高波动小盘 / 大票）、哪些题材，每晚名额 | 进攻态点高波动题材小盘；2026 年那类状态转向大票 |
| 交易 | 做不做、做多大、做多还是做空、止损和离场松紧 | 进攻态早买、收盘才止损、放大仓位；防守态不开新多，只做第一次跌破 50 日线后的反抽空 |
| 衔接 | 名额和仓位分给哪档、同时持仓上限、换仓 | 进攻态名额给新起来的题材 |

规则：

1. **先共同版本，后修正。**行情层冻结之前，只能改 `common`。
2. **状态最多 3 种，开关最多 2 个**，每个开关都要逐字对应他的一句原话。先做市场级；题材级（2026 年 7 月的差异在题材层面，指数看不出来）等市场级冻结、漏斗显示仍有按题材丢的段时再开。
3. **每条线每个状态最多 2 项修正**，修正幅度要能说清理由（共同版本加收缩修正，防止小样本凑数）。
4. **有他样本的状态**：修正按行情段（episode）留一检验。**没有样本的状态**：按原话写，标“未观测”，不参与选择，冻结后由前向记录检验。
5. **分状态的目标画像来自他的台账**：先按年、按月、按状态核对他做多还是做空、做哪档票、什么形态，再对照我们系统的月度盈亏。不能直接采信统计检验的 p 值。台账逐年记录密度不同，不比笔数密度。
6. **行情状态只读市场数据和本系统已知的点名**，不读他的台账、段表和账户结果。

## 四、各线的尺子与接受条件

所有线都要满足：选择年（Martin：2024、2025）只用于选择，留出年（2026，标“留出*”）只测一次；+3 段以内的差别算噪音。

### 行情层

- 定义来自他的原话和标准参数，只取常见值，不做拟合。
- 冻结条件：
  - 定义扰动后的日重合率 ≥ 90%；
  - 在 config 写死的参照账户上（Martin：master、M3B），选择年每年都是进攻日收益高于防守日；
  - 他的台账在有样本的状态上方向说得通（只报告，不足标“未观测”）。
- 冻结后写入 `state.json.components`，三条线引用同一份。

### 选股线

- 口径：每晚新点 K=3 只、10 晚冷却（S 口径）。
- 主尺：他的段在早期合格夜被点到的段数。
- 护栏：不限 K 时平均每晚新点名 ≤5；每年点过的不同票数不比比较对象多 20% 以上。
- 接受：选择年合计 +3 段，且每年都不降。
- 分状态报告：各状态下他的段被点到的比例。

### 交易线（测试台）

- 输入：他的每一段，在 [首锚点−3, 峰前1日] 内每晚都把他的票当作“已点名”，买点、止损、仓位、离场全由我们的执行决定。
- 对照：同一晚我们点名里不是他的票，用同一个执行一起跑。
- 主尺：他的段峰前一日仍持有的段数，以及在他的段上的盈亏比和平均 R。
- 护栏：对照票合计不比比较对象差；行为记分卡（胜率、盈亏比、持有天数）在 ±20% 内的项数不减。
- 接受：峰前持有 +3 段，他的段平均 R 不降，护栏都满足。
- 这个测试台只用来评执行；最终系统的策略代码仍然不许读他的台账（三层对照第二层）。

### 衔接线

- 输入：选股线和交易线的冻结版本。
- 主尺：持仓漏斗里“点到 → 早买 → 峰前持有”的转化。
- 接受：峰前持有 +3 段，选择年每年不亏。

### 合并验收

- 持仓漏斗（以冻结段表为分母，每段按最早丢失的层只计一次）：

  | 层 | 含义 |
  |---|---|
  | L0 | 不在池 |
  | L1 | 未点名 |
  | L2 | 未触发 |
  | L3 | 未成交 |
  | L4 | 买晚 |
  | L5 | 早买后被洗 |
  | L6 | 峰前持有 |

  其中 L0–L1 归选股线，L2–L3 归衔接线，L4–L5 归交易线。
- 接受新的合并主线需同时满足：
  - 选择年每年不亏；
  - 峰前持有合计比当前合并主线多 3 段以上，且每年都不少；
  - 峰前持有段的仓位占比不降；
  - 行为记分卡在 ±20% 内的项数不减。
- 还没有合并主线时，比较对象用底线参照（Martin：master）。底线参照只作比较对象，不作底座：候选不得沿用它的成交额排序选股。
- 各项按状态分开报告。资金纯度、毛利纯度、撒网比例只报告，不做门槛。

## 五、每轮怎么走

| 步骤 | 做什么 | 模型 |
|---|---|---|
| 量 | 核对规则指纹；读上一轮 Codex 写好的 `STATUS.json`（各线 × 各状态：当前值、目标、可达上限、冻结版本），不跑重计算 | Sonnet，低推理 |
| 定格 + 设计 | 见下文 | Opus |
| 审查 | 独立挑错，最多改两次。清单见下文 | Opus |
| 跑 | Codex 执行：预登记 → 选择 → 留出一次 → 报告 → `pipeline.accept` 判定 → 重出 `STATUS.json` | Sonnet，低推理（只负责启动和等待） |
| 核对 | 流程：时间顺序、只用选择年、登记版、看板和判定代码未改、测试全过。数字：从 json 复算关键数，漏斗分层之和等于段数，重算判定 | Sonnet |
| 记账 | 照抄已核对的判定，写总账和 state | Sonnet，低推理 |

**定格 + 设计**：

- 挑一个格子，也就是“哪条线 × 哪个状态（或 common）”。
  - 规则：先看合并漏斗丢段最多的线；再看该线可补段数，即 min(离目标的差, 可达上限 − 当前值)。
  - 前一轮有线被接受时，本轮必须做合并验收。
- 查总账，写清和旧轮次差在哪。
- 从他的原话和漏斗逐段数据两个角度出方案。
- 写任务书，最多 5 个候选。

**审查清单**：

- 未来函数；策略侧是否读了他的台账、票名、日期、段表；
- 选择和留出是否分开；参照账户和比较对象是否事先写死；可达上限是否先算；
- 是否只改了声明的线和格子；
- 翻译和实现上的老坑：宽止损配固定风险导致仓位太小（H1）；小试仓占满名额（H2）；加仓后止损没跟上（H2）；过滤过严导致可达上限过低（H2）；冷却挡住再买（P5）；止损只有约半个 ADR、盘中被扫（P5）；选错参照账户（P5）；
- 是否与总账中失败的轮次实质重复；
- 执行时点单测是否先写。

每轮约 6 个 agent，其中 Opus 2 个；审查每改一次多 2 个。

**检查点**（满足任一就停下，交给用户）：

- 本次运行跑满预定轮数（默认 3 轮）；
- 同一格连续 2 轮没有进步；
- 审查两次都没过；
- 留出年一次检验亏钱；
- 规则漂移；
- 固定卡失败；
- 合并验收达到成功标准。

## 六、工作目录

`studies/<trader>/workflow/` 下放这些文件：

| 文件 | 内容 |
|---|---|
| `config.json` | `goal`、`hard_lines`、`accept`、`checkpoint` 四节（用户节）；选择年、留出年、段表与 SHA、底线参照、参照账户、系统注册表 |
| `state.json` | 各线冻结版本（`regime` / `selection` / `trading` / `conversion` / `merge`）、`components`、`pending_merge`、`next_round`、最近几轮记录、`bootstrap_done` |
| `attempts.jsonl` | 总账，一行一轮。字段：id、日期、`line`、`scope`（common 或状态名）、改了哪几节、机制、对应原话、主尺结果、收益、结论、报告路径、教训 |
| `rounds/WFnn/` | 本轮的 PLAN、PREREG、量表、REPORT_CN.md、核对结果、DECISION_CN.md |

## 七、Codex 子步骤

- 不开 fast 或 priority：不加 `service_tier`。
- 模型 `gpt-6.1-sol`，推理强度 max。
- 同一时间只跑一个重计算单元，`CPUQuota=60%`，最多两核。

```bash
cd <worktree> && n=<id>; d=studies/<trader>/workflow/rounds/$n; mkdir -p $d/logs; LOG=$PWD/$d/logs/codex.log
systemd-run --unit=codex-$n --collect -p CPUQuota=60% -p AllowedCPUs=0-1 -p Nice=10 -p IOSchedulingClass=idle \
  -p StandardOutput=file:$LOG -p StandardError=file:$LOG -E HOME=/root -E PATH="$PATH" --working-directory=$PWD \
  codex exec -m gpt-6.1-sol -c model_reasoning_effort="max" --dangerously-bypass-approvals-and-sandbox \
  "按 $d/PLAN_CN.md 执行。任务书就是全部要求。" </dev/null
```

等待时不用前台 `sleep`。重复执行下面这条，直到单元结束：

```bash
pid=$(systemctl show -p MainPID --value codex-$n); [ "$pid" != 0 ] && timeout 570 tail --pid=$pid -f /dev/null; systemctl is-active codex-$n
```

磁盘剩余低于 800MB 时，只清理本轮自己的重复中间文件。
